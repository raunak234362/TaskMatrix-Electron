# TaskMatrix Desktop

TaskMatrix Desktop is an Electron application for Whiteboard Technologies (WBT). It provides a desktop interface for the TaskMatrix project and operations management system. The UI is built with React and communicates with a separately hosted TaskMatrix API and Socket.IO service; this repository contains the desktop client, not the backend.

## What the application covers

The client brings together project and drawing coordination, work breakdown structures and milestones, tasks, RFQs, submittals, RFIs, change orders, estimates and invoices, vendors and fabricators, team and employee tools, reports, calendar, notes, and real-time chat and notifications. Available screens and actions depend on the signed-in user's role and backend permissions.

## Requirements

- Node.js (use the current LTS release) and npm.
- A working network connection to a compatible TaskMatrix backend.
- A TaskMatrix account to sign in. The backend owns authentication, application data, file storage, and authorization; there is no local/demo backend in this repository.
- For packaging, a build environment supported by Electron Builder. Native packaging requirements vary by target OS; build each platform on its supported host where possible.

## Configure before running

Create a `.env` file in the repository root. `.env` is ignored by Git. Set the API URL to the backend's `/v1/` endpoint:

```dotenv
VITE_BASE_URL=https://your-taskmatrix-host.example/v1/
```

`VITE_BASE_URL` is required for normal API requests, file links, and the Socket.IO host. The client derives the socket host by removing `/v1/` and appends `/v1/` for API requests. Keep the trailing slash and use the URL scheme and host that your backend serves.

If the Socket.IO endpoint uses a different origin from the API, set its origin separately. This value is also used as the Vite development proxy target:

```dotenv
VITE_SOCKET_URL=https://your-taskmatrix-host.example
```

When omitted, the socket URL and proxy target are derived from `VITE_BASE_URL`. The Vite config contains a deployed WBT host as a proxy fallback, but set your intended backend explicitly for local development and release builds.

The optional GitHub commit dashboard can use credentials to increase GitHub API rate limits or access private repositories. Add only the tokens relevant to the GitHub owners configured in the dashboard:

```dotenv
VITE_GITHUB_TOKEN_WBTIT=your_read_only_token
VITE_GITHUB_TOKEN_RAUNAK=your_read_only_token
```

Without these values, public repository requests can still work subject to GitHub's unauthenticated rate limits. `VITE_*` values are embedded in the renderer bundle and can be extracted from a distributed app. Do not put write-capable or otherwise sensitive credentials here; use narrowly scoped read-only access and treat any bundled token as public.

The GitHub Actions release workflow expects repository secrets named `VITE_BASE_URL`, `VITE_SOCKET_URL`, `VITE_GITHUB_TOKEN_WBTIT`, and `VITE_GITHUB_TOKEN_RAUNAK` when it creates its build environment. GitHub token secrets may be omitted if the optional integration does not need them. Set the URL secrets to the deployment you intend to ship against.

## Install and run

```bash
npm install
npm run dev
```

The development command starts Electron and the Vite renderer. Sign in using an account provisioned by the configured backend. Browser-based Vite requests under `/v1` are proxied to the configured backend target.

To preview the compiled Electron application locally:

```bash
npm run build
npm start
```

## Build installers

Build commands compile the app and package it for the selected platform:

```bash
npm run build:win
npm run build:mac
npm run build:linux
```

For an unpacked directory build, use `npm run build:unpack`. Artifacts are generated by Electron Builder (normally under `dist/`). Installer targets and app metadata are defined in [`electron-builder.yml`](electron-builder.yml). Packaged builds check for updates through `electron-updater`; release publishing is configured for the GitHub repository in that file.

## Project layout

```text
src/
  main/       Electron main process: window, native notifications, PDF export, updates
  preload/    Small, context-isolated bridge between renderer and Electron
  renderer/   React UI, routes, Redux state, API services, and Socket.IO client
build/        Platform packaging assets and macOS entitlements
resources/    Application icon and packaged resources
```

The Electron/Vite entry points and renderer aliases are configured in [`electron.vite.config.mjs`](electron.vite.config.mjs). The React renderer uses Redux Toolkit for shared state and Axios service modules for backend requests. The preload exposes a limited `window.api` bridge for OS username lookup and invoice PDF export, along with the Electron Toolkit API. Backend requests add the signed-in session token as a Bearer token; real-time connections pass that token as Socket.IO auth.

## Troubleshooting

- **API calls fail or login cannot complete:** check `VITE_BASE_URL`, backend availability, and whether the account is enabled on that backend. Restart `npm run dev` after changing `.env`.
- **Socket chat/notifications do not connect:** check that the Socket.IO service is reachable at `VITE_SOCKET_URL` (or the derived API host), and inspect the Electron DevTools console for connection errors.
- **Files fail to open:** the app requests file endpoints from the configured backend and may need an authenticated session. Confirm the backend URL and the signed-in user's access.
- **GitHub dashboard is rate-limited:** configure a narrowly scoped read-only token for the matching owner, or wait for the unauthenticated quota to reset.
- **Linux notifications:** the main process routes notifications through an in-app toast on Linux; macOS and Windows use native notifications when supported.

## Development notes

- Keep backend URLs and credentials out of committed source. `.env` is ignored, and production builds should receive their configuration from the release environment.
- The renderer is sandboxed by Electron context isolation and uses the preload bridge for native operations. Extend that bridge deliberately when adding main-process features.
- No backend service or database setup is provided here; coordinate API changes with the TaskMatrix backend project.
